# PRD Quality Review — Boosty TV (prd-boosty-tv-2026-10-25)

Reviewed: `prd.md`, `addendum.md`, `.memlog.md` (owner decisions treated as settled). Spot-checked against `EXPERIENCE.md`, `docs/feature-parity.md`, `docs/api-contract.md`, `docs/android-tv-auth-playback-spike.md`, `CLAUDE.md`. Review date: 2026-10-25.

## Overall verdict
A disciplined, well-anchored PRD: every FR cites a parity ID or is flagged [IMPROVEMENT], all endpoint references resolve to `api-contract.md`, exclusions (comments, payment, download, in-app install) are explicit and consistent, and the thesis ("remote-native navigation + a session that doesn't drop") is carried through into metrics and counter-metrics. The main risks are in the MVP boundary and in unverified facts stated as settled: the P1 slice includes sign-out but its only entry point (Настройки) is P2, the P1 sidebar shows P2 destinations with no defined P1 behavior, and P1 resume (UJ-2, SM-4) rests on an E9→E8 `timeCode` round-trip that `api-contract.md` §8 lists as unverified and that §10 Open Questions does not mention. These are fixable without restructuring; once fixed the PRD is ready for architecture and epics.

## Decision-readiness — adequate
Decisions are stated as decisions and attributed (phone-auth exception to the CLAUDE.md "no custom form" rule in §4.1, public repo and GitHub Releases in FR-55, 95 % / 30 s threshold in FR-49, sign-out moved to P1 in §7.2). Trade-offs are named where they matter: Live streams are not fetched on Главная because "polling every Author would cause a request storm" (§4.3), Continue history is device-local because there is no backend (§6), external player loses Progress tracking (FR-50). The risk table (§9) is specific and tied to spike scenarios.

The weak spot is §10 Open Questions: a single bundled line ("E18 Events format, subscriptions pagination, video duration in the Feed, and 429/404 shapes"). Several unverified facts that P1 FRs depend on are written as settled instead of being surfaced. No `[NOTE FOR PM]` callouts exist; for a personal app with an engaged owner that is acceptable, but the open items below should be visible.

### Findings
- **high** P1 resume rests on an unverified server round-trip (§3 Glossary "Progress", FR-43, FR-15, SM-4) — The Glossary states Progress is "Stored on the server (E9, `timeCode`)" and FR-15 says OK "opens the player at the server Progress", but `api-contract.md` §8 item 8 lists "Whether E9 progress is reflected in `timeCode` on the next E8" as unverified (spike S8). UJ-2's climax and SM-4 depend on it, and there is no stated fallback (e.g. local last-known position in Continue history) if the round-trip is delayed, partial or absent. *Fix:* add this to §10 with its spike ID, and state the P1 fallback in FR-43/FR-15 (e.g. "if fresh E8 `timeCode` is missing or older than the locally recorded position, resume from the local position") or explicitly make the fallback a decision deferred to spike S8 results.
- **medium** Open Questions under-reports known unknowns (§10) — Missing: E8 accepting `comments_limit=0` (api-contract §8.5; FR-32 states it as fact), phone-auth error shapes / captcha / code delivery channel (FR-1 hedges but §10 omits; S2), refresh-token lifetime and rotation (only in §9 risks), signed-URL TTL and CDN error status (S7; FR-48 trigger depends on it). *Fix:* list each with the spike scenario that closes it (S2, S4, S5, S7, S8, S11) so architecture and story writers see them in one place.

## Substance over theater — strong
No persona theater: one household, one owner, a "family member" who appears only where she changes behavior (UJ-2, shared device). Vision (§1) is product-specific and falsifiable ("the owner stops opening BoostBuddy"). NFRs are mostly product-specific (NFR-2 error-class list, NFR-3 named mutation endpoints, NFR-6 11 sp minimum). Minor furniture: NFR-6 "Everything works with the remote alone" restates SM-5/CLAUDE.md, and NFR-8 portability is a restatement of CLAUDE.md rather than a requirement with a check — both harmless.

### Findings
- **low** NFR-5 performance is adjectival (§5 NFR-5, FR-13) — "stay smooth with hundreds of items" and FR-13 "The list stays smooth with hundreds of posts" are bounded only by an `[ASSUMPTION]` target to be set in P3. *Fix:* state a provisional measurable bound now (e.g. "500-item feed, D-pad held 10 s, no dropped focus moves and no frame > 50 ms in a perf trace on the test device") and mark it provisional.

## Strategic coherence — strong
The thesis is explicit in §1 (parity minus comments, plus remote-first navigation and a durable session) and the metrics validate it: SM-2 for the session bet, SM-3/SM-5 for remote-first, SM-1 for the overall switch. Counter-metrics SM-C1–C3 directly guard against gaming SM-2/3/4 and match CLAUDE.md rules. Phase tags follow the CLAUDE.md delivery phases, and the P1 set maps onto the CLAUDE.md vertical slice ("sign in → subscriptions/feed → post → authorized video → resume → return with restored focus") plus Continue watching, which UJ-2 genuinely needs.

The MVP is coherent as a problem-solving slice, with one boundary defect below.

### Findings
- **high** P1 slice references P2 surfaces (§7.1, FR-8, FR-9, FR-53, UJ-7) — FR-8 Sign out is [P1] (owner decision) and UJ-7 starts "Настройки → confirm", but the Settings screen (FR-53) is [P2]; P1 has no entry point for sign-out. Likewise FR-9 lists Поиск and Настройки in the sidebar while search (FR-26–31) and settings (FR-53) are P2, and nothing says what those sidebar items do in P1 (hidden, placeholder, or minimal screen). Epic planning will either drag FR-53 into P1 or ship a dead-end sidebar item, which CLAUDE.md forbids ("no dead-end navigation"). *Fix:* either promote a minimal Настройки (version + «Выйти из аккаунта») to P1 and keep «Системный видеоплеер» and Diagnostics in P2, or add to FR-9: "In P1 the sidebar shows only sections whose FRs are delivered; Поиск is hidden until P2; Настройки appears with sign-out only."
- **low** SM-1 starts after P3 (§8) — the primary thesis metric cannot be observed until the end, so P1/P2 have no thesis signal. Acceptable for a personal app; optionally add an informal P1 checkpoint ("owner uses P1 for a week for video-only viewing").

## Done-ness clarity — adequate
Most FRs carry testable consequences: FR-4 ("N concurrent requests ... exactly one refresh request"), FR-7 (exact wipe list), FR-10 (exact Back order), FR-13 (opaque offset, dedup by id, `isLast`), FR-41a (two OK presses, re-fetch E10, no auto-retry), FR-45 (5 s auto-hide with explicit exceptions), FR-49 (95 % / 30 s). Where behavior is delegated to EXPERIENCE.md the delegation is explicit. Gaps remain in a few P1 FRs that stories will lean on.

### Findings
- **medium** FR-49 conflates "finished" with "end of playback" (FR-49) — "At the end of a video (≥ 95 % watched or < 30 s left ...), the player writes the final Progress, exits to its origin". Read literally, the player exits at 95 % / 30 s left, cutting off the last part of the video (credits, an after-credits remark). EXPERIENCE.md "Ended" has the same ambiguity. *Fix:* split it: "A video counts as finished when ≥ 95 % watched or < 30 s left (removed from Continue history, MediaRow «Просмотрено»). The player exits to its origin only when playback reaches the actual end, or when the user exits."
- **medium** SM-4 is not guaranteed by FR-44 (FR-44, SM-4) — "at most once per ≥ 10 s of movement" sets a minimum interval but no maximum, so nothing bounds how stale the last write may be; SM-4 promises ±10 s "including after sleep or a reboot", and a power-off/unplug does not deliver a lifecycle callback. *Fix:* phrase the throttle as an interval ("every 10–15 s of playback, plus on pause/background/Stop/exit/end"), and scope SM-4 to "graceful" interruptions (sleep, Back, Home, OS reboot) with a separate looser bound for power loss.
- **medium** Continue history is under-specified for a P1 FR (FR-15, Glossary) — "recently played, unfinished video Media" with no definition of "recently", no maximum length, no ordering rule beyond UJ-2's "first", and no behavior when an entry's post becomes Locked or 404. It also needs a duration/position to render «осталось 12 мин» (UJ-2) when Feed duration is unverified. *Fix:* add: stored fields (postId, mediaId, blogUrl, last position, duration if known, updatedAt), cap (e.g. 20), order (most recently played first), and removal rules (finished, 404, Locked → removed or shown as Locked).
- **medium** «Версия» does two things (FR-54, FR-56) — FR-54 reveals Diagnostics after seven OK presses on «Версия»; FR-56 runs an update check "on «Версия» in Настройки". Seven presses would fire seven GitHub requests (unauthenticated limit 60/h per addendum) and possibly a notice that interrupts the Diagnostics gesture. *Fix:* debounce (one check per press burst / per N minutes) and state that the notice does not interrupt the seven-press sequence, or move the manual check to a separate «Проверить обновления» action.
- **low** FR-39 sleep assumption is garbled (FR-39) — "Playback continues while the TV screen saver or sleep is suppressed" does not say whether the app suppresses the screen saver during audio or whether audio continues when the screen saver starts. *Fix:* state the intended behavior ("While audio plays, the app keeps the screen awake" or "Audio keeps playing under the screen saver; it pauses on device sleep") and keep the S9 assumption tag.
- **low** Player entitlement failure has no FR (FR-42/FR-48 vs EXPERIENCE.md "Плеер" row) — EXPERIENCE.md defines "Media not entitled → exit with a no-access message"; FR-48 only covers recovery, and NFR-2 only says the class is distinguished. *Fix:* add one consequence to FR-48: a no-access error does not trigger re-resolve and exits with the no-access message.
- **low** FR-46 omits the "no automatic quality" case — EXPERIENCE.md QualityOption: "If no quality can be picked automatically (PLAY-02), the quality list opens before playback starts." *Fix:* add as a consequence of FR-46 (P1).
